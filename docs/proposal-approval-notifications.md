## 1. 为什么要做这件事

现在这条链路是**单向**的：

```
语雀文档 → yqa 判定 → plan.json → crb 提交 → 学校审核 → ？？？
```

最后一段是断的：**社员问「我那个教室批了吗」，没有任何人知道答案。**
只能人工登录办事大厅一页页看。这份方案就是把最后一段接上。

## 2. 为什么放在本项目，而不是 yqa

负责人提到「crba 和 yqa 似乎都可以」。三条硬约束把答案定死了：

1. **yqa 没有学校登录态，而且这是它刻意守住的边界。**
   上游 `docs/handoff.md` §1.1 明确写着：「它**没有**登录南大办事大厅的能力，
   也**不查**任何教室占用情况」。把轮询塞进 yqa，等于让一个只读语雀的程序
   开始持有学校凭证 —— 那条边界是它的安全落点，不该破。
2. **只有这一侧能查学校系统**（`crb borrow list`），而「审批结果」这个数据
   **只存在于学校系统里**。数据在哪一侧产生，就该在哪一侧取。
3. **`crb` 已经把这件难事做完了**：`crb borrow list --json` 会带回
   `SHZT`（状态）、`FJ`（房间）、`KSRQ/KSJC/JSJC`（时间）等字段。
   轮询要写的新代码只有「比对 + 留痕 + 出文档」。

**但结果的投递侧仍然在 yqa（或它下游）** —— 因为「通知谁」这件事需要
语雀侧的身份映射（人名 → QQ 号），而那张表的持有者在
`qqbot`/`yqa` 那边（见上游 `handoff.md` §3.4）。所以分工是：

```
crb-agent 只负责：查 → 比对 → 写文档（谁的手机号都没有）
yqa/qqbot 负责：读文档 → 映射到人 → 发通知
```

这条分工的好处：**本项目不碰任何身份信息**，产出的文档是纯粹的
「申请单号 + 结果」，给谁看由下游决定。

## 3. 轮询

### 3.1 什么时候轮询

```
每 10 分钟（±60s 抖动，别让请求整点撞在一起）：
  1. crb_status —— 登录态不可用就直接跳过这一轮（不是错误，别刷日志）
  2. crb borrow list --json（当前学期）
  3. 与账本比对 → 发现新结束的申请 → 记账 → 重生通知文档
```

* **登录态失效不算故障**：跳过，日志留一行，等负责人扫码（`/agent/auth`）。
  这就是负责人说的「如果 crb 内的 auth 有效……」（auth 无效就别轮询）。
* **间隔为什么是 10 分钟**：审批是老师手动点的，分钟级足够；
  而学校接口有风控（`crb` 里已有 403 → 刷新 `_WEU` Cookie 的处理），
  没必要更密。做成 `CRBA_NOTIFY_INTERVAL` 可配。
* **只读**：轮询永远不写学校系统，只有 `borrow list`。这一点要写进代码注释，
  免得后人顺手加个「自动重试提交」。

### 3.2 一个人写账本

轮询进程是账本**唯一**的写者（上游那次事故的教训：两个写者会互相覆盖）。
所以它是**独立单元**，不是 `crb-agent.service` 里的一个线程：

* 网页服务重启/挂掉不影响继续跟踪审批；
* 「谁是唯一写者」一眼可见，不用在进程里再加锁。

网页那边（agent）只**读**这份账本 —— 于是可以回答
「我这周期的申请都批了吗」，但不会与轮询抢写。

> 手动重跑一次（比如负责人刚扫码恢复登录态，不想等 10 分钟）：
> `sudo systemctl start crb-agent-notify.service`（`Type=oneshot` 的那个版本，
> 走同一个 flock）。不提供「网页上点一下刷新」——那会引入第二个写者，
> 得不偿失。

## 4. 数据：账本与对外文档

### 4.1 只追加的账本（内部）

`<outbox>/approval/ledger.jsonl`，一行一条，**只追加，永不重写**：

```jsonc
{"sqbh": "7e75…1041", "first_seen_ended": "2026-09-27T10:25:30+08:00",
 "status": "approved_assigned", "snapshot": { /* 那一轮的原始记录，原样存 */ }}
```

`schemaVersion` / `applicationId` / `sourceDoc` 这些**不存进账本**：
它们是「重生文档」时现算的（§6）。账本只记**事实**：
「这个 SQBH 在什么时候第一次被看到『已结束』，结束成什么样」。

为什么要留 `snapshot`：字段名可能会变，而**当时看到的原始记录**是唯一能
事后复盘的东西。这也是我们**目前**唯一能用来反推
`approved_assigned` / `rejected` 字段的地方（见 §5）。

### 4.2 对外文档（每轮重生）

`<outbox>/approval/notifications.json`，**每轮从账本整个重写**：

```jsonc
{
  "schemaVersion": "nova.classroom-borrow-notification.v1",
  "batchId": "notification-2026-09-27T10:30:00.000Z",
  "generatedAt": "2026-09-27T10:30:00.000Z",
  "notifications": [ /* 账本里全部已结束的结果，按 detectedAt 排序 */ ]
}
```

* 里面**永远是全部**已结束的结果（满足「追加所有已经审批结束的结果」），
  但文件本身是重生的 —— 因为 `notificationId` 稳定（§6），
  下游按 id 去重，所以**重跑、重启、手抖都不会重复通知**。
* `batchId` / `generatedAt` 描述的是**本轮**，供人看「这份是什么时候生成的」。
* 重生的好处：早期条目写错了还能修（纯追加的单文件做不到 —— 那是我没选的方案）。

## 6. 关联：SQBH ↔ 语雀侧的 applicationId / sourceDoc

学校记录里只有 `JYYTMS`（用途描述）、日期、节次 —— 没有语雀的任何 id。
而通知里要带 `applicationId` 与 `sourceDoc`。所以要在两侧之间建映射。

**匹配键 = （日期 + 节次 + 标题）**（负责人已选）。数据来源：

1. 读 `<outbox>/plan.json` 的 `activities`，那里有溯源键
   `_application_id` 与 `_doc_id`（上游 `handoff.md` §2.2 的约定）；
2. 周期翻转后 plan.json 会被搬进 `outbox/archive/<周期>/`，所以还要**扫归档**；
3. 标题要对齐：`crb` 提交时会把 `JYYTMS` 写成 `"<title>（意向：<room>）"`,
   匹配时剥掉「（意向：…）」再比。

**匹配不上的怎么处理**（重要，不要静默）：

* 学校的申请在本周期清单里找不到 → 写进 `<outbox>/approval/unmatched.json`，
  带上原始记录与「为什么认不出」。人看一眼就知道是「有人手工在学校系统里
  提交的」还是「标题被改过」。
* **绝不猜**：猜错了会把 A 活动的结果安到 B 头上，比认不出严重得多。

> 为什么不用「把 applicationId 写进用途描述」这个更精确的办法：
> 那会改动学生在办事大厅看到的文案（`JYYTMS` 是给人看的），
> 而且**已经提交的历史申请没有它**。负责人也选了这个方案。

## 7. `notificationId` 怎么「稳定生成」

同一个结果重复生成必须得到同一个 id，否则下游去重失效。所以：

```
notificationId = "notify-" + sha1(f"{sqbh}|{status}|{实际教室列表}").hexdigest()[:8]
```

* **不含时间戳** —— 含了就每轮都变，去重立刻失效（这是最容易犯的错）。
* **含「实际教室列表」**：审批结果从「已通过未分配」变成「已通过 + 教室」时，
  这是一条**新**通知，应该再发一次（社员想知道教室定了）。
* 按 §0 的约定，`approved_unassigned`（批了但没教室）**不进通知文档** ——
  等它变成 `approved_assigned` 才发。所以 `unassigned` 状态只记在账本里，
  用来做「上轮是 unassigned、这轮变 assigned」的转换检测。

`type` 与 `result.status` 的映射：

| 学校侧判定 | `type` | `result.status` | `actualRooms` | `feedback` |
|---|---|---|---|---|
| 通过且已分配 | `"approved"` | `"approved_assigned"` | 分配的教室（数组） | `""` |
| 退回 | `"rejected"` | `"rejected"` | `[]` | 审核意见 |
| 通过但未分配 | —— **不进文档**，只记账本 | | | |

## 8. 落在哪、yqa 侧要同步改什么（负责人点出的问题）

写进 `<outbox>/approval/`（上游的产出目录里），因为取件的下游已经在那儿了。
但**上游有几处约定要一起改**，否则会打架 —— 这正是负责人担心的那点：

| # | yqa 侧的改动 | 为什么必须改 |
|---|---|---|
| Y1 | **归档时跳过 `approval/`** | 周期翻转会把 `outbox/` 整批搬进 `archive/<周期>/`。审批结果是**跨周期**的（9 天窗口跨周），被搬走就等于下游读不到 |
| Y2 | **`sync-guide` / 根目录节点顺序**里说明 `approval/` | 那是「程序产出的固定位置」之一，不该让人以为是垃圾 |
| Y3 | 通知 vocabulary 要不要加 `approved` / `rejected` | 如果希望**同时**走 QQ 通知（而不只是给下游读文件），需要在上游的 `kind` 表里加两个，并写提示词例子 |
| Y4 | `plan.defaults.json` 的 PII 提醒是否覆盖 `approval/` | `approval/` 里**只有单号与结果**，没有姓名手机号 —— 所以**没有**这个风险，写清楚免得后人误判 |

**Y1 是硬依赖**：不改的话，跨周期那一刻审批结果会被搬进归档目录，
下游读到的是空的。我建议先在 yqa 里加一行「跳过 `approval/`」，
再上轮询 —— 顺序反了会丢数据。

> 另一条路（供比较）：让 yqa 只多一个「转发」动作，把 `approval/` 里的
> 新通知转成它自己的 `kind=approved` 事件（复用现有的
> `outbox/notify/pending/` 投递队列）。好处是 QQ 桥不用改；
> 代价是 yqa 要新增一类程序发的通知。**这条要不要做，请一起定。**

## 9. 系统设计

| 单元 | 类型 | 干什么 | 唯一写者 |
|---|---|---|---|
| `crb-agent.service` | 常驻（已存在） | 网页界面 + agent；**只读**账本 | 自己的 session 留痕 |
| `crb-agent-notify.service` | 常驻（新） | 轮询 → 比对 → 记账 → 重生文档 | `approval/ledger.jsonl`、`approval/notifications.json` |

新命令：

```bash
crba notify-poll            # 常驻轮询（给 systemd）
crba notify-once            # 只跑一轮，打印发现了什么（人工排查用，不写文件）
crba notify-show            # 打印当前账本的概要（给 agent 工具用）
```

`notify-poll` 与 `notify-once` 共用同一段逻辑，区别只是循环与否；
两者都取 flock，所以「手动跑一次」不会和常驻的抢。

给 agent 加一个只读工具 `approval_status`：读账本，回答
「这个周期哪些批了、哪些退了、哪些还没动静」。这样「查审批进度」这个问题
就不必每次都去打学校接口。

**验收**（写进 `docs/deploy.md`）：

```bash
systemctl is-active crb-agent-notify
journalctl -u crb-agent-notify -n 20 | grep "notify 轮询开始"
# 账本是只追加的：跑两次 notify-once，行数不涨（幂等）
```
