# 对照：同学的浏览器插件 vs 我们的 crb

> 对照对象：`教室借用自动填写.user.js`（`ehall 教室借用 · 活动工作台 v0.14.1`，
> `@namespace NOVA.Classroom.Borrow`，2026-09-27 由负责人转来）。
> 目的：**允许 cac 自由选择用插件还是用 agent**，所以要把「两边会不会打架」
> 说清楚，而不是「谁更好」。
>
> 结论先行：**能共存**。两边都调同一批学校接口、都用「查申请记录」做去重，
> 而 crb 的去重比插件**更保守**，所以最坏情况是「少提交一条」而不是「重复提交」。
> 但有一处**必须实测确认**的字段差异（§3），在确认前不要混用两种工具。

---

## 1. 它是什么

一个油猴脚本，挂在办事大厅的教室借用页面上跑（`@match .../jwapp/sys/jsjy/*`），
在页面里长出一个「活动工作台」面板：自动填表 + 读申请记录 + 导入上游的
`plan.json` 批量提交。**它驱动页面表单**，也直连接口（`fetch` 那三个 `.do`）。

它比我们最初以为的完整得多：它认上游 `yuque-agent` 的契约
（`nju-yuque-agent.application.v2` / `nju-yuque-agent.plan`），也认一个我们没见过的
信封格式 `nova.classroom-borrow.v1`。

## 2. 能力矩阵

| 能力 | 插件 | crb（我们） |
|---|---|---|
| 查空闲教室 | `cxkxjs.do` ✓ | `crb free`（同一接口）✓ |
| 查申请记录 | `cxjsjysq.do` ✓，还能导出 JSON / CSV | `crb borrow list --json` ✓ |
| 存草稿 | `TYPE=save` ✓ | `crb plan --save` / `borrow draft` ✓ |
| 正式提交 | `TYPE=TJ` ✓ | `crb plan --submit` / `borrow submit` ✓ |
| **撤回** | ✗ | `crb borrow withdraw` ✓ |
| **删除** | ✗ | `crb borrow delete` ✓ |
| **改一条已有申请** | ✗ | `crb borrow edit` ✓ |
| 在**页面上**自动填表 | ✓（核心功能，含下拉/日期/原生 input 事件） | ✗（不走界面，直连接口） |
| 表单预检 | ✓（提交前校验字段） | ✗（后端拒了才知道） |
| 导入 plan.json | ✓ | ✓ |
| 记录生命周期分类 | ✓ 草稿 / 进行中 / 需人工确认 | ✗（只给 `SHZT` 原值 + 一个字典） |
| 去重判定 | 日期+校区+节次**完全相同**+教室匹配 = `strict`；时段重叠+教室匹配 = `probable` | **日期 + 节次重叠**即判 `duplicate` |
| 去重**键** | `applicationId`（`plan.json` 的 `_application_id`），缺了就报「无法稳定去重」 | 无（只按时间比对） |
| 批量提交 | ✓（`batch-submit-preview`） | ✓ |
| 登录方式 | 借浏览器已有会话 | `crb login`（Playwright）/ 服务端扫码 |

一句话：**接口层是同一套（三个 `.do` 完全重合），差异在「谁去填表」和「怎么判定重复」。**

## 3. ⚠️ 必须实测确认：`JSJYLXDM` 用了两套字典

两边都给 `xzjasjysq.do` 的同一个字段 `JSJYLXDM` 填值，但**填的值不一样**：

| | 取值 | 字典 |
|---|---|---|
| 插件 | `09` | `{教师教学、补课: 01, 团学活动: 09, 考试: 10, 讲座: 11}` |
| crb | `02` | `{01 辅导员, 02 学生社团管理部, 03 就业指导中心, 04 国际合作与交流处, 05 学生工作处, 06 校团委, 13 待悦读课程管理}` |

同一字段名、两套互斥的字典，而且 `01` 在两边的含义就冲突
（插件=「教师教学、补课」，crb=「辅导员」）。

**已知的一半**：同学给的记录样本里，列表接口返回的是
`"JASJYLXDM": "05"` + `"JASJYLXDM_DISPLAY": "学生工作处"` —— 这与 **crb 的字典一致**
（crb 自己也把 `JASJYLXDM` 当作 `JSJYLXDM` 的别名）。但那一条**不一定是插件提交的**，
所以还不能据此判定谁对。

**怎么定案**：登录态恢复后调一次借用类型字典接口（crb 已封装：
`api.borrow_types()` → `cxjsjylx.do`），看学校到底认哪些码。
在确认之前，**不要让两种工具交替提交同一批申请**——否则学校侧看到的申请类型
可能不一致，而这类差异在「审核不通过」之前不会有任何提示。

## 4. 共存分析：会不会打架

两边都靠「查申请记录列表」去重，所以关键是**判定标准谁更保守**：

```
插件 strict  = 日期 + 校区 + 节次完全相同 + 教室匹配
crb duplicate = 日期 + 节次重叠（不看校区、不看教室）
```

* **插件提交过 → 我们再看**：日期与节次必然相同 → crb 判 `duplicate` → **跳过**。
  不会重复提交 ✓
* **我们提交过 → 插件再看**：日期相同、节次相同、校区相同；
  教室那一项看 `JYYTMS`（crb 会把意向教室写进用途描述「意向：xxx」）
  与 `JASMC`/`FJ` 的匹配。**如果 crb 当时没写意向教室**，插件的 `sameRoom` 为假
  → 落不到 `strict`，可能被判成「需要人工确认」而不是「已存在」——
  **不会自动重复提交，但会提示人**。这是可接受的（人看一眼就知道）。

**结论：crb 更保守，所以「混用」的方向上不会造成重复申请。**
代价是 crb 可能会**误拦**：同一天同一时段、两个不同活动的申请（例如上午一个活动、
下午另一个活动但节次区间有重叠），crb 会判 `duplicate` 而插件不会。

> 这正是负责人说的「两个不同的活动撞时段很正常」。**本轮按原逻辑保留**
> （`crb` 未改）。如果将来要按「重要字段是否全部相同」去重，正确的做法是
> 用 `applicationId`（见 §5），而不是再加几层字段比较。

## 5. 值得向插件学的两点（**未实现，供决定**）

1. **`applicationId` 当稳定去重键。** 插件明确说「缺少 `application_id`
   无法稳定去重」，而 `plan.json` 的每条 activity 本来就带 `_application_id`。
   如果我们把「提交时 → 落一条 `SQBH ↔ applicationId` 的映射」，去重就能精确到
   「这一条我交过没有」，上面那种误拦就消失了，而且两边用的是**同一个键**。
2. **记录生命周期分三档**（草稿 / 进行中 / 需人工确认），而不是把 `SHZT` 原值丢给人。
   插件是这么分的（`recordLifecycle()`）：
   * `暂存` 或 `SHZT=00` → 已有草稿
   * 含 `撤回|不通过|驳回|拒绝|退回|取消` → **需人工确认**（← 这就是「退回」的判定）
   * 含 `待|审核|通过|提交|完成` → 进行中
   这套中文关键词判定**正好补上了我们拿不到的「退回」字段语义**，见
   [`proposal-approval-notifications.md`](proposal-approval-notifications.md) §5。

## 6. 明确不做的

* **不合并两个工具**。插件驱动页面、我们直连接口，服务对象不同（插件给
  「想看着表单一步步走」的人，agent 给「把清单丢过来」的人）。
* **不复制插件的自动填表**。走页面就要跟着学校的 DOM 改版走，那是插件已经
  承担的维护成本；我们直连接口更稳。
